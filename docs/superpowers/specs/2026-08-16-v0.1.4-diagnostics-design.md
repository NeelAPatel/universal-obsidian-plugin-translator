# UOPT v0.1.4 diagnostics design

## Goal

Make translation failures self-explanatory in the UI without changing UOPT's translation architecture. v0.1.3 already captures exact per-file errors in `file.lastError` and returns structured translation errors; v0.1.4 must preserve and surface that information instead of collapsing it into a generic failure summary.

## Scope

v0.1.4 adds structured diagnostics for failed translation attempts.

### Activity

Normal successful/info activity entries remain compact.

Failed translation activity entries show a concise summary containing:

- plugin
- file
- failure category
- short error message
- provider
- model
- batch number when known

Error entries are expandable. Expanded details show:

- stage/category
- exact error
- file
- provider
- model
- batch / total batches when available
- number of candidates in the batch when available
- timestamp

Actions:

- Copy error
- Retry file

### Plugin Detail / file table

A file with a failed translation attempt visibly shows a failed/error state. Selecting that file exposes its most recent translation failure details near the file controls/preview area.

The file-level failure view includes Copy error and Retry file actions.

### Failure categories

UOPT normalizes failures into one of:

- Provider connection
- Provider response
- Provider format
- Translation validation
- File changed
- Filesystem
- Unknown

The original error message is always retained.

### Diagnostic data model

Store structured diagnostic data on the file record as `lastFailure` while continuing to populate `lastError` for backward compatibility.

`lastFailure` contains only serializable fields, including:

- category
- stage
- message
- provider
- model
- file
- batch
- totalBatches
- candidateCount
- timestamp

Successful translation clears `lastFailure` and `lastError` for that file.

### Batch attribution

The translation pipeline must track the currently executing batch so that provider/format failures can identify the batch that failed. This requires propagating batch metadata through the provider/translator boundary without changing translation semantics.

### Retry behavior

`Retry file` retries only the selected approved failed file, not the entire plugin. It uses the current saved provider settings and the existing plugin context. It reuses the normal translation/validation/snapshot safety path rather than implementing a separate write path.

### Error classification

Classification is deterministic and based on the stage plus known error patterns/types. Raw exception text remains available in details.

Examples:

- empty/no provider text -> Provider response
- malformed/non-JSON structured response -> Provider format
- JS/JSON syntax validation failure -> Translation validation
- target hash changed before write -> File changed
- read/write/rename errors -> Filesystem
- provider request/connectivity failure -> Provider connection when identifiable, otherwise Provider response/Unknown

## Approaches considered

1. **Raw error text only** — cheapest change, but still leaves users guessing where the error occurred and cannot support reliable retry UX.
2. **Structured file diagnostics (chosen)** — small extension to existing state, clear UI, actionable retries, and enough metadata for debugging without introducing a logging subsystem.
3. **Full debug console / persistent trace log** — highest observability, but too much scope and noise for v0.1.4.

## Testing

Add tests for:

- diagnostic classification
- batch metadata preservation on provider failure
- file `lastFailure` persistence and clearing after success
- retrying only one failed file
- Activity error rendering with expandable details
- Copy error payload content
- file table/detail failed state
- existing translation safety tests remain unchanged

## Non-goals

- no translation-engine redesign
- no new provider
- no full request/response body logging
- no background telemetry
- no external logging service
- no change to scan behavior or localization filtering
